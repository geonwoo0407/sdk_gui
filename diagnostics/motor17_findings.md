# 17번 모터 토크 이상 조사 (2026-09-17)

## 02:16 사용자 실측 로그 분석

- `mx_bus_20260917_021645_528269.jsonl`: 17~22번 PING이 각 3회 모두 timeout(-3001). 사용자가 **첫 실행 때 모터 전원이 꺼져 있었고 두 번째 전에 켰음**을 확인했다. 따라서 이 실행을 배선/U2D2 불량의 증거로 사용하지 않는다.
- `mx_bus_20260917_021654_813501.jsonl`: 전원 인가 후 약 6초간 모든 ID에서 RAM 30회 + 설정 1회 = **각 31/31회 성공**, 총 186회 읽기 실패 0. 모든 Status Packet 오류도 0이었다.
- 전부 Torque=0, Hardware Error=0, Bus Watchdog=0. 전압은 17번 12.6V, 18·19·21·22번 12.7V, 20번 12.9V. 온도는 26~28°C. 이는 정지·토크 OFF 조건의 측정으로 동작 중 전압 강하·과열·접촉 불량을 배제하지 못한다.
- 전원 인가 후의 오류 0은 **이전 증상 당시 오류가 없었다는 증거가 아니다**. 과거 보호정지를 확인하려면 재부팅 전 오류를 읽어야 한다.
- 모든 ID의 모델 321, 펌웨어 45, 위치제어 모드 3, Drive Mode 4, PWM Limit/Goal PWM 885, Current Limit/Goal Current 2047, Position P/I/D 850/0/0이 동일했다. 17번만 출력 제한/PID가 낮은 설정 차이는 발견하지 못했다. 전류 제한의 영향은 제어 모드에 따라 다르므로 이 값을 올려 해결할 근거도 없다.
- Return Delay: **17·21번 500µs (=0.5ms)**, 나머지 0µs. 이는 응답 패킷 전송 전 대기시간이며 500µs는 제조사 기본값이다. 불일치는 확인했지만 이번 통신은 모두 성공했다. 이 차이만으로 패킷 충돌이나 토크 차단을 단정하지 않는다.
- Shutdown 설정: 17~21번은 **52 = 0x34 (과부하·전기적 문제·과열)**, 22번은 **4 = 0x04 (과열만)**. 22번에는 과부하/전기적 문제에 대한 해당 자동 토크 차단 비트가 꺼져 있다. 17번의 보호를 줄여 22번에 맞추는 방식으로 해결하지 않는다. 이 설정 차이만으로 17번 고장 원인을 확정할 수 없으며, 18·20번은 17번과 같은 보호 설정이다.
- 호스트 USB latency는 여전히 16ms. 개별 읽기 지연 중앙값은 17번 11.49ms, 18~22번 약 15.85~15.89ms였다. 전체 통신 지연의 개선 대상이지만 17번만의 응답 실패는 관측되지 않았다. 이 수치는 이번 개별 83/64바이트 읽기 조건이며 GUI의 SyncRead 주기 실측과는 다르다.

현 시점 결론: 토크 OFF 조건에서 U2D2부터 여섯 모터까지 읽기 경로는 정상 동작했다. U2D2 또는 Molex의 간헐적 불량을 확정하거나 배제할 자료는 없다. 다음 유효한 측정은 **증상 발생 직후 로봇을 지지하고, 전원 재인가·토크 재조작 없이 GUI를 종료한 뒤 진단 도구를 실행하는 것**이다. 이때 Torque와 Hardware Error, 각 ID의 응답 여부를 확인한다. 필요하면 이후 전원을 끄고 한 요소씩 배선 교차 시험을 진행한다. 이번 분석에서도 모터 설정은 변경하지 않았다.

## 확인한 내용

- 사용자가 설명한 증상: 처음에는 버티다가 동작 중 힘이 풀림. 같은 분기의 19·21번 동시 이상 여부는 미확인.
- 실행 중이던 프로그램은 `python3 sdk_gui.py`이며 ROS 노드가 아니다. `/dev/ttyUSB0`, Protocol 2.0, 4,000,000 bps를 사용한다. 17~22번은 GUI 구성상 MX-106이다. 실제 모델은 진단 시 PING으로 확인해야 한다.
- 최초 확인한 GUI PID 7625의 시작 시간은 00:44:15 KST. 표준 출력/오류는 `/dev/pts/2`로 향했고 로그 파일은 열려 있지 않았다. 코드에도 파일 로그 저장이 없다. `.ros/log`의 최신 파일은 5월 기록으로 현재 GUI의 통신 이력이 아니다. 터미널 스크롤백이 남아 있다면 별도 증거가 될 수 있다.
- 커널 기록: 00:34:14, 00:34:16 USB 분리, 00:34:18 `device descriptor read/64, error -71`, 이후 ttyUSB0 재등록. 최초 GUI 실행 시간 이후에는 USB 분리/리셋 기록을 찾지 못했다. 원문: `usb_history_20260917.txt`.
- 이는 PC–U2D2 USB 경로의 과거 오류 증거이며 17번 모터의 통신 오류 증거는 아니다. 장치 재연결 과정의 오류만으로 U2D2 본체, USB 케이블, PC 포트를 구별할 수 없다. 모터 쪽 TTL/RS-485 오류는 커널 USB 로그 없이도 발생할 수 있다.
- `/sys/bus/usb-serial/devices/ttyUSB0/latency_timer` = **16 ms**. 고속 피드백 지연에 영향을 줄 수 있지만 17번만 토크가 풀리는 원인으로 확정할 수 없다.
- `sdk_gui_state.json`의 토크 설정 포함 프레임 1,933개와 `robot_motions.json`의 325개를 확인했으며, 17~22번의 OFF 설정은 없었다. 저장 데이터에 17번만 OFF로 지정된 문제는 발견하지 못했다.

## 코드에서 확인한 진단 한계

- `sync_torque`: `write1ByteTxOnly`의 송신 결과만 확인하고 ON/OFF를 표시한다. 모터 수신/적용 확인은 없다.
- `set_all_torque_on`: SyncWrite를 보내기 전에 버튼을 ON으로 표시하고, 송신 성공 후 실제 Torque Enable(64)을 다시 읽지 않는다. 따라서 화면의 ON은 실제 토크 유지 증거가 아니다.
- `refresh_live_joint_angles`: 현재 위치만 읽으며 10회 연속 읽기 실패 시에만 경고한다. 간헐적 실패 통계가 저장되지 않는다.
- 설치된 SDK의 `GroupSyncRead.rxPacket`은 모터별 Status Packet 오류 바이트를 버리며, 한 ID의 수신 실패에서 전체 읽기를 중단한다. 기존 SyncRead 실패 로그만으로 문제 ID를 확정할 수 없다.
- Hardware Error Status(70), 전압(144), 온도(146), 전류(126)를 읽어 기록하는 경로가 없다. 보호정지 후에도 GUI의 ON 표시가 남을 수 있다.
- `read_torque_enabled`는 재탐색 등에서 사용하지만 토크 ON 직후나 동작 중 지속 확인용으로 연결되어 있지 않다.

## 실측 방법

최초 조사 시에는 GUI 종료를 확인했으나, 측정 시작 전 새 GUI 프로세스(PID 11521, 01:23:32 시작)가 포트를 다시 점유해 측정하지 못했다. 이후 사용자가 02:16에 직접 측정한 결과는 문서 상단에 추가했다. 아래 판정표는 후속 진단 기준이다. GUI 코드나 모터 설정은 이번 조사에서 변경하지 않았다.

로봇을 안정적으로 지지하고 GUI 및 다른 시리얼 프로그램을 종료한 상태에서:

```bash
python3 diagnose_mx_bus.py --samples 30 --interval 0.2
```

- PING/READ만 사용한다. 모터 토크, 목표 위치, EEPROM, 모터 통신 속도는 변경하지 않는다.
- 다른 프로세스가 포트를 점유하면 열기 전에 중단한다. 열린 동안에는 시리얼 포트의 배타 접근을 요청한다.
- 모델 321(MX-106 Protocol 2.0)만 레지스터를 해석한다.
- 각 ID를 개별적으로 읽어 전체 SyncRead 실패와 구분한다. Alert 비트와 통신 실패를 별도로 기록한다.
- 원시 응답, 오류, 토크, 하드웨어 오류, 전압, 온도, 전류, 목표/현재 위치, 제어 모드, PWM/전류 제한, PID, Shutdown 설정을 `diagnostics/mx_bus_*.jsonl`에 저장한다.
- 정지 상태의 짧은 반복 측정이다. 성공하더라도 동작 중 순간 전압 강하, 접촉 불량, 통신 손실을 배제할 수 없다. GUI 종료에 따른 통신 공백은 활성화된 Bus Watchdog에 영향을 줄 수 있다.
- 전원을 껐다 켜면 현재 오류 상태가 사라질 수 있으므로, 이상 발생 직후의 읽기가 가장 유용하다. 보호정지 원인을 확인하기 전에 반복 ON/재부팅으로 증거를 지우지 않는다.

## 판정 기준과 배선 분리 시험

| 관측 결과 | 해석 / 다음 확인 |
| --- | --- |
| 응답 정상, Torque=0, Hardware Error=0x20 | 모터가 과부하를 감지한 증거. 관절 부하·간섭·동작 조건·모터 상태 확인. 통신 불량이라고 단정하지 않음. |
| 응답 정상, Error=0x04 | 과열 감지. 온도와 냉각·부하 확인. |
| Error=0x01 또는 0x10 | 입력전압 이상 또는 전기적 문제/전력 부족 단서. 전원 분기, VDD/GND 압착, 모터 커넥터의 부하 시 전압 확인. |
| 17번만 응답 실패 | 17번 개별 배선·커넥터·모터·중복 ID를 우선 확인. U2D2를 바로 배제할 수는 없음. |
| 17·19·21 동시 실패, 18·20·22 정상 | 같은 U2D2/같은 통신 채널을 공유한다면 오른쪽 분기의 중계보드 포트·공통 전원/접지·배선을 우선 확인. |
| 양쪽 전반 동시 실패 및 USB 분리 | USB 케이블/PC 포트/U2D2 또는 전체 전원·버스 문제를 확인. |
| Torque=1, 오류 없음, 힘이 약함 | 제어 모드/PWM 제한/모드별 전류 제한/PID·목표 오차·기계적 전달부 비교. 토크 비트 ON이 실제 출력 보장은 아님. |

교차 시험은 전원을 끄고 핀 배열·전압·TTL/RS-485 종류가 같은 연결끼리, 한 번에 한 요소만 바꾼다.

1. 17번 케이블/압착 핀을 검증된 동종 케이블로 교체해 비교한다. 오류가 사라지면 해당 연결부 가능성이 높아진다. 재체결 효과일 수도 있어 반복 확인이 필요하다.
2. 같은 사양의 중계보드 분기 포트를 교환한다. 문제가 특정 포트에 남는지, 케이블/모터를 따라가는지 확인한다.
3. 17번을 검증된 짧은 배선으로 연결해 같은 조건에서 비교한다. 모터를 따라 이상이 남으면 모터/부하/설정 가능성이 높다.
4. 동일 배선·전원·부하를 유지하며 USB 케이블, PC 포트, 마지막으로 U2D2를 하나씩 교체한다. U2D2만 교체했을 때 반복적으로 개선되어야 본체를 강하게 의심할 근거가 된다.

Molex 접점은 DATA뿐 아니라 VDD/GND의 접촉 저항 증가로도 영향을 줄 수 있다. 정지 시 전압이 정상이더라도 동작 중 순간 강하는 이번 저속 읽기로 놓칠 수 있다. 필요하면 모터 측 전압을 부하 중 계측한다. U2D2는 모터 전원을 공급하지 않으므로 전원 분기를 별도로 구별해야 한다.
