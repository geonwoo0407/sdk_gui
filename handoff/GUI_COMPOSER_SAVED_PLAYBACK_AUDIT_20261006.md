# 시퀀스 조합 → 저장 → 모션 제작 재생 차이 조사

조사일: 2026-10-06. 모터 포트를 열거나 로봇을 움직이지 않았다. GUI 소스 및 모션 데이터는 수정하지 않았다.

## 결론

**모션 제작 탭의 관절 궤적 그래프가 재생 타이머와 같은 스레드를 막는 성능 문제를 재현했다.** 동일한 저장 프레임과 시작각으로 실행해도, 그래프가 보이는 조건에서 목표각 쓰기 호출 간격이 약 5ms에서 약 57ms로 벌어졌다. 같은 모션 재생 경로에서 그래프 갱신만 멈추면 약 5ms로 복구됐다.

실제 보행 당시의 USB 쓰기/읽기와 관절 피드백 로그는 없으므로, 이번 넘어짐/이상 보행의 유일한 원인이라고 확정하지 않는다. 다만 화면별 차이를 설명하는 구체적인 소프트웨어 결함과 그 지연 효과는 확인했다.

## 저장 및 목표 생성 검증

현재 소스에서 해당 함수를 AST로 추출해 하드웨어를 여는 생성자 없이 실행했다.

1. `build_composed_sequence_frames(False)`와 `True` 결과가 모두 `..`와 일치했다. 이 구성의 원본 배속은 1.0이다.
2. 실제 `save_composed_sequence()` → `load_saved_sequence()` → `play_motion_page_sequence()` 경로에서 프레임 각도, 시간, lift 옵션, 반복 경계가 그대로 유지됐다. 불러올 때의 정렬 함수도 실행했다. UI 표시와 파일 쓰기만 모의 처리했다.
3. 같은 시작각과 정확히 같은 가상 tick 시각을 주면 조합 경로와 모션 경로의 목표각 쓰기 905건이 모두 일치했다.

따라서 이번 데이터에서 저장/불러오기가 각도나 시간, 보간 방식을 바꾼다는 증거는 없었다. 이 검증은 실제 이벤트 루프 지연이나 모터 추종을 포함하지 않으므로 아래 실험을 별도로 수행했다.

## Qt 이벤트 루프에서 확인한 차이

실제 Qt `PreciseTimer` 5ms와 현재 코드의 `anim_step()`, `scrub_timeline()`, `JointTrajectoryWidget`을 사용했다. 그래프 크기는 1200×320, 표시 관절은 ID 22이다. 32프레임과 시작 자세는 모든 조건에서 동일하다. 쓰기는 각도와 시각을 기록하는 함수로 대체하고 읽기는 지연 없는 모의 응답으로 처리했다. 이 수치는 **모터로 나간 패킷 간격이 아니라 쓰기 함수 호출 간격**이다.

| 조건 | 호출 간격 중앙값 | 최대 간격 | 전체 쓰기 호출 | 반복 실험 |
|---|---:|---:|---:|---:|
| 조합 경로, 모션 그래프 숨김 | 5.17~5.18ms | 5.36~5.40ms | 907~908회 | 2회 |
| 모션 경로, 그래프 표시/갱신 | 57.21~57.63ms | 59.35~61.90ms | 107~114회 | 2회 |
| 모션 경로, 그래프 샘플 계산만 캐시 | 5.18~5.21ms | 13.41~14.07ms | 792~855회 | 2회 |
| 모션 경로, 그래프 표시 후 갱신 고정 | 5.17ms | 5.44ms | 909회 | 1회 |

원래 그래프의 궤적 샘플 계산만 약 49~50ms, 전체 그리기는 약 57~58ms였다. 모션 경로를 유지한 채 갱신만 정지한 조건에서도 지연이 사라졌으므로, 조합용 시간 변환 함수의 차이가 이 실험 결과를 만든 것은 아니다.

샘플 계산만 캐시하면 큰 지연은 줄지만 13~14ms의 최대 지연이 남았다. 계산 캐시 하나만으로 실기 5ms 주기를 보장한다고 주장할 수 없다. 실제 화면 크기, 전체 위젯 그리기, CPU 부하, USB 읽기/쓰기를 포함하면 수치는 달라진다.

## 코드 경로와 보행에 미치는 영향

- `sdk_gui.py:1646`: 재생 `QTimer`가 GUI 스레드에서 5ms 간격으로 `anim_step()`을 호출한다.
- `sdk_gui.py:5087`: 현재 벽시계 경과 시간으로 타임라인 시각을 계산한다. 반복 경계에서는 마지막 목표 전송/피드백 후 시계를 다시 시작한다.
- `sdk_gui.py:5187`: `scrub_timeline()`에서 목표각을 계산한다. UI 갱신 때 `trajectory_graph.update()`도 요청한다 (`5275`).
- `sdk_gui.py:834`: `trajectory_samples()`가 그래프를 그릴 때마다 수백 개 시점의 `timeline_state_at()`을 다시 계산한다. 표시 관절은 하나지만 각 시점에서 여러 프레임의 관절/토크 정보를 처리한다.
- `sdk_gui.py:863`: `paintEvent()`가 위 계산과 전체 그래프 그리기를 GUI 스레드에서 수행한다.
- 그래프는 모션 제작 탭에 배치되어 있다 (`3342`). 조합 탭에서는 해당 그래프가 숨겨져 있어 그리기 비용이 발생하지 않는 조건이 된다.
- 현재 시각 기반 재생이므로 GUI가 막힌 동안 누락된 중간 목표를 모두 순서대로 전송하지 않는다. 다음 tick에서 더 뒤의 시각을 평가하며 프레임 종점 보장과 반복 경계 처리는 별도로 수행한다.

`..`의 발 들기 프레임은 62ms이고 `lift_early_arrival=True`라 목표 궤적은 앞 80%, 즉 49.6ms에 완료되도록 계산된다 (`5474`). 그래프 한 번 그리는 시간이 그보다 길다. 이로 인해 여러 중간 목표가 빠지고 큰 폭으로 변한 목표를 한 번에 쓰는 상황이 재현됐다.

예를 들어 첫 번째 모의 실험에서 ID 20의 연속 목표각 사이 최대 차이는 그래프 숨김 2.29°, 그래프 표시 12.125°였다. 이는 **명령 목표의 변화량**이다. 실제 관절이 그만큼 즉시 움직였다는 뜻도, 해당 실험이 실제 관절 추종을 측정했다는 뜻도 아니다.

## 최소 수정 방향과 후속 검증

아직 적용하지 않았다.

1. 재생 동안 전체 궤적 샘플과 정적인 그래프를 캐시한다. 프레임/초기각/선택 관절/표시 크기 등이 바뀔 때 다시 만들고, 재생 중에는 현재 시각 표시만 가볍게 갱신한다. 데이터 변경 시 캐시 무효화가 필요하다.
2. 같은 블록 스타일을 매번 재설정하는 작업도 활성 블록이 바뀔 때로 제한한다. 이것이 별도 주원인이라고 측정한 것은 아니다.
3. 실제 하드웨어 검증에서는 동일한 시작 자세와 저장 데이터로 양쪽 경로의 TX 시작/끝, RX 시작/끝, 실제각, 경계 시각, paint 시작/끝을 함께 기록한다. 버퍼에 기록하고 재생 종료 후 파일로 저장해 로깅 자체의 지연을 줄인다.
4. UI 최적화 후에도 통신/화면 지연이 남으면 모터 통신과 제어 스케줄을 GUI 이벤트 루프에서 분리하는 변경을 검토한다. 통신 포트 접근을 한 곳으로 모으고 UI 접근은 Qt 신호로 처리해야 한다.

각도, 도착 허용 오차, 발 들기 보간 비율, 각 프레임 도착 대기 정책은 이번 성능 문제 해결을 위해 임의로 변경할 항목이 아니다.
