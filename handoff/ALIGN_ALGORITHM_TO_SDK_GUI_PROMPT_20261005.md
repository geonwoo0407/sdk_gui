같은 모션을 GUI에서 실행하면 넘어지지 않지만 알고리즘에서 실행하면 넘어지는 문제가 있습니다. 알고리즘의 실제 모터 실행 경로를 첨부한 최신 `sdk_gui.py`의 실기 시퀀스 재생 동작에 맞춰 수정해 주세요. GUI를 알고리즘에 맞추거나 배속만 임의로 낮추는 것이 목표가 아닙니다. 정상 실행의 목표각 궤적, 시간 처리, 시작 자세, 반복/연결 경계와 모터 설정을 일치시키는 것이 목표입니다. 넘어짐의 원인은 아직 확정하지 않았으므로, 코드 차이와 실제 측정 결과를 구분해 주세요.

아래 내용은 2026-10-05 현재 GUI 작업 파일을 읽어 확인한 기준입니다. 실제 실행 중인 GUI와 알고리즘의 소스·바이너리·모션 JSON도 이 기준과 같은지 먼저 확인해 주세요.

1. **사용할 원본과 비교 범위**

   첨부한 `sdk_gui.py`, `sdk_gui_state.json`, `sdk_gui_timing_repairs.json`, `robot_motions.json`을 기준으로 삼아 주세요. 오래된 원격 GUI, 과거 SDK 압축 파일, 테스트용 가짜 SDK만 보고 구현을 판단하지 마세요. 알고리즘 명령 → 모션 선택 → runtime JSON → 실제 플레이어 → 실제 하드웨어 백엔드 → Dynamixel 통신까지 호출 경로를 추적해 주세요.

   현재 확인한 저장 상태에는 시퀀스 495개, 배포 체크 모션 75개가 있고 `robot_motions.json`에도 75개가 있습니다. 체크된 모션의 이름별 `frames`, `repeat_count`, `playback_speed`는 현재 JSON과 일치합니다. 다른 PC의 JSON도 같다는 뜻은 아니므로 양쪽 파일 해시와 실제 선택된 모션 내용을 비교해 주세요. 현재 GUI에서 편집한 내용이 아직 저장되지 않았거나 재생 UI 배속/반복이 저장값과 다를 수도 있으므로 실제 실행값을 함께 기록해 주세요.

   모션 제작/시퀀스 조합의 연속 재생과 라이브러리의 단일 프레임 이동은 별도 경로입니다. 단일 프레임 이동은 저장된 프레임 시간(최소 5ms)을 사용하고 시퀀스 배속을 적용하지 않으며 피드백 호출 빈도도 다릅니다. 비교 대상을 먼저 일치시켜 주세요.

2. **실제 GUI 재생 경로와 목표각 생성**

   `start_motion_playback()` → `anim_step()` → `scrub_timeline()` → `write_goal_positions()`가 기준입니다. `frame_motion_progress()`, `interpolate_angle_shortest()`, `angle_to_dxl_position()`도 함께 확인해 주세요. 파일 상단에 남은 구형 설명이나 현재 호출되지 않는 `command_time_profile_frame()`을 재생 기준으로 삼지 마세요.

   GUI는 PC에서 매 제어 tick의 중간 목표각을 계산하여 Goal Position을 전송합니다. 보간식은 다음과 같습니다.

   ```text
   elapsed = clamp(timeline_ms - start_ms, 0, time_ms)
   ratio = 0.8 if lift_early_arrival is true
                   and name contains any of [발들, 들기, 오들, 왼들]
               else 1.0
   u = min(1, elapsed / max(1, time_ms * ratio))
   progress = (1 - cos(pi * u)) / 2
   delta = ((target_deg - start_deg + 180) % 360) - 180
   goal_deg = start_deg + delta * progress
   ```

   C++의 음수 나머지 처리 때문에 Python `%`와 결과가 달라지지 않도록 해 주세요. 발 들기 규칙은 이름과 `lift_early_arrival=true`를 모두 만족할 때만 적용합니다. 앞 80%에 최종 목표각 명령에 도달하고 뒤 20%는 유지하며, 프레임 총길이를 80%로 줄이는 기능이 아닙니다. 실제 모터의 도착이 보장된다는 의미도 아닙니다. `[착지]`에 별도의 내부 가감속 프로파일을 추가하는 경로는 현재 GUI 시퀀스 재생에서 사용하지 않습니다.

   소수 각도를 보존하고 ID, degree/radian, 방향, 영점, 오프셋을 확인해 주세요. GUI 원시 위치 변환은 각도를 ±180도 범위로 감은 뒤 표현 가능한 범위로 제한하고 `round(2048 + angle_deg * 4096 / 360)`을 사용하며 결과는 0~4095로 제한합니다. Python 반올림의 경계값도 비교해 주세요. 프레임에 없는 관절을 0도로 초기화하지 말고 이전 명령 자세를 보존하세요.

3. **시작 자세, 모터 프로파일과 설정**

   GUI는 새 실기 재생 직전에 필요한 관절의 Present Position을 다시 읽어 첫 프레임의 시작각으로 사용합니다. 첫 프레임의 목표각으로 즉시 점프하지 않습니다. 이후 프레임은 이전 목표 자세를 이어서 보간하고 매 tick 현재각을 새 시작점으로 삼아 궤적을 다시 만들지 않습니다. 반복에서는 직전 최종 목표 자세를 이어받습니다. 별개의 새 재생 요청과 내부 반복/연속 조합은 구분해 주세요.

   GUI의 준비 코드는 펌웨어 42 이상을 확인하고 Drive Mode bit 2(`0x04`)를 토크 OFF 상태에서 준비합니다. 그러나 실제 시퀀스 재생은 Profile Acceleration(108)과 Profile Velocity(112)를 **둘 다 0**으로 설정한 뒤 PC 중간각을 반복 전송합니다. 각 프레임의 최종각과 이동시간을 한 번 보내는 방식이나 매 tick 내부 시간 프로파일을 재설정하는 방식으로 대체하지 마세요. 기존 저수준 함수가 duration을 최소 1ms로 제한한다면 GUI와 같은 프로파일 0 송신 경로를 구현해 주세요.

   Protocol 2.0, baudrate 4,000,000, GUI 관절 ID 범위 0~22를 사용합니다. Goal Position(116, 4byte)은 GroupSyncWrite, Present Position(132, 4byte)은 GroupSyncRead입니다. 통신 포트는 GUI에서 탐색하며 `/dev/ttyUSB0`은 최후의 기본값입니다. 알고리즘에서도 실제 연결된 장치를 확인하세요.

   GUI는 실행할 때 Operating Mode, PID, 전류/PWM 제한을 일괄 재설정하지 않습니다. 현재 작업 폴더의 C++ 하드웨어 생성자에는 Position Mode 설정과 PID 850/0/0 설정이 있습니다. **이 값을 GUI의 실제 설정으로 가정하면 안 됩니다.** 정상 동작하는 GUI 조건에서 모터 ID별 모델, 펌웨어, Operating/Drive Mode, PID, 전류/PWM/위치 제한, Homing Offset, 방향을 읽어서 비교하고 알고리즘 초기화가 이를 바꾸는지도 기록해 주세요. 미측정 항목은 추정하지 말고 미확인으로 남겨 주세요. 생성자만 실행해도 토크나 설정이 변경될 수 있으므로 모터 없는 검증에서는 실제 하드웨어 객체를 만들지 마세요.

4. **제어 주기와 실제 통신 지연**

   GUI는 `Qt.PreciseTimer` 5ms, 즉 목표 200Hz로 제어하고 `time.perf_counter()`의 단조 증가 시계로 경과시간을 계산합니다. 고정 tick 수에 5ms를 곱해서 시간으로 삼지 마세요. 시퀀스의 위치 피드백은 마지막 읽기 시작 기준 10ms 이상 경과했을 때 호출하며 종료/반복 경계에서는 강제 읽기도 있습니다. UI 갱신은 약 30fps, 정상 피드백 로그는 10Hz로 제한됩니다.

   이것은 설정값입니다. 동기식 SyncRead와 Qt 이벤트 처리로 실제 목표 송신 간격이 5ms보다 길어질 수 있으며 이번 조사에서 실측 200Hz를 확인하지 않았습니다. 단일 프레임 이동은 매 제어 호출에서 피드백을 읽는 경로이므로 시퀀스의 10ms 조건과 구분하세요.

   조사 PC의 `/sys/bus/usb-serial/devices/ttyUSB0/latency_timer` 읽기값은 16ms였습니다. 대상 알고리즘 PC/Jetson의 값은 별도 확인해 주세요. USB latency를 임의로 낮추는 것만으로 재생이 일치했다고 판단하지 마세요. 동일한 모션에서 목표 송신 간격, SyncRead 소요시간, 경계 처리 시각, 전체 시간을 측정해 두 환경을 비교해 주세요.

5. **타임라인, 배속, 반복과 조합 저장**

   `start_ms`는 해당 타임라인의 시작 시각, `time_ms`는 프레임 길이입니다. 실제 한 사이클의 끝은 `max(start_ms + time_ms)`이며 `max_seq_ms`는 화면 범위일 수 있으므로 이것까지 기다리지 마세요. 처음 공백은 시작 자세를, 중간 공백은 직전 목표 자세를 유지하는 대기입니다. 프레임은 정렬하며 겹침 처리도 GUI와 동일해야 합니다.

   일반 저장 모션의 시간에는 저장된 `playback_speed`를 한 번 적용합니다. 저장 전 조합 재생에서는 원본 모션 배속과 조합 전체 배속을 모두 적용하며, 조합에서 추가한 앞 대기에는 원본 배속을 적용하지 않고 전체 배속만 적용합니다.

   **조합을 저장/내보낼 때 원본 모션 배속은 이미 프레임 시작/끝 시각에 반영됩니다. 저장된 JSON을 실행할 때 원본 배속을 다시 적용하지 마세요.** JSON의 `playback_speed`만 추가로 적용합니다. 예를 들어 원본 65ms에 0.9배속이 반영돼 약 72ms로 저장되고 전체 배속이 1.05라면, 그 저장 프레임의 명목 이동시간은 약 `72 / 1.05`ms입니다. 원본 0.9를 다시 나누면 중복 적용입니다. 정확한 정수 ms는 시작/끝의 공유 경계를 반올림한 차이로 계산합니다.

   조합 프레임에는 내부 반복이 이미 펼쳐져 있을 수 있습니다. 펼쳐진 반복과 저장된 전체 `repeat_count`를 구분하고, `lift_early_arrival`와 `playback_cycle_end`를 로더에서 버리지 마세요. `composer_entry_frames()`, `composer_timing_segments()`, `build_composed_sequence_frames()`를 기준으로 검증하세요.

6. **프레임 끝, 반복 경계, 완료와 다음 모션 연결**

   GUI는 프레임 끝에서 정확한 최종 목표각을 전송하고 실제 도착을 기다리지 않습니다. `gate_timeline_on_frame_arrival()`이라는 이름과 달리 현재 이 함수는 허용오차 gate가 아닙니다. 타이머가 경계를 넘어오면 해당 tick에서 경계를 처리하되 일반 프레임 경계에서는 재생 시작 시계를 바꾸지 않고 다음 tick은 실제 경과시간을 따릅니다. 프레임 활성 구간은 기본적으로 `[start, end)`이며 전체 최종점과 내부 사이클 끝 처리는 별도로 있습니다.

   반복 끝과 `playback_cycle_end`에서는 최종 목표 전송과 피드백 처리를 마친 뒤 다음 사이클의 시계를 재시작합니다. 따라서 경계 통신 시간이 실시간 실행 길이에 영향을 줍니다. 이 처리를 단순한 평탄화나 절대 마감시간 따라잡기로 제거하지 마세요. `anim_step()`, `next_playback_cycle_end()`, `restart_playback_cycle()`를 그대로 비교하세요.

   전체 자연 종료도 위치 도착을 기다리지 않고 최종 목표를 유지합니다. 현재 GUI export에는 `completion = {position_tolerance_deg: 2.0, settle_duration_ms: 80, settle_timeout_ms: 3000}`가 들어가지만 GUI 재생은 이를 도착 대기에 사용하지 않습니다. 알고리즘 쪽의 5도/80ms/3000ms 설정과 혼동하지 마세요.

   알고리즘의 매 프레임 도착 대기와 최종 settling이 정상 타임라인에 추가 대기를 만드는지 확인하고, GUI 호환 실행에서는 이 대기로 타이밍을 변경하지 않도록 수정하세요. `settle_duration_ms=0`만 바꿔서는 위치 gate가 사라지지 않을 수 있습니다. 이 모드의 완료 이벤트는 '계획한 최종 목표 전송 종료'이며 '실제 도착 확인 완료'와 구분해서 API에 표현해 주세요.

   알고리즘의 다음 명령 연결에서도 중복 실행, 반복의 중복 적용, 불필요한 기본자세 복귀, 추가 안정화 대기, 실행 중인 모션의 선점/취소가 있는지 확인하세요. GUI 조합으로 실행한 것과 별도 명령을 연속 호출한 것의 시작 자세 및 경계 처리가 같은지도 검증하세요.

7. **토크, 보정, 통신 실패 처리**

   GUI는 재생 준비에서 필요한 모터의 연결·토크 상태를 확인하고 프로파일을 준비합니다. 토크 ON에는 현재각을 Goal로 미리 맞추는 절차가 있습니다. 하지만 프레임 JSON의 `torques`를 읽어 매 프레임 토크를 켜고 끄지는 않습니다. 자연 종료 때 자동으로 토크를 끄지도 않습니다. 일시정지/중지는 활성 실기 프레임에서 피드백 자세를 홀드하는 경로입니다.

   현재 GUI는 목표 송신 실패 시 재생 실패 처리하지만 재생 중 피드백 읽기 실패만으로 자동 중단하지 않으며, 읽은 위치 오차로 궤적 속도를 자동 보정하지 않습니다. **정상 타이밍을 맞추는 것과 기존 알고리즘의 통신 장애·비상 정지 처리를 없애는 것은 별개입니다.** 정상 실행 경로를 먼저 맞추고 장애 처리 차이는 명시적으로 보고하세요. 송신 성공을 모터 수신/실제 도착 확인으로 간주하지 마세요.

   알고리즘에서 추가하는 관절 override, 영점/방향 보정, 상체·보행 보정이 있다면 적용 전/후 목표각을 기록해 GUI 입력과 비교하세요. 최초 궤적 비교에는 같은 입력 각도를 사용하고, 이후 실제 운영 보정이 결과를 어떻게 바꾸는지 별도로 검증하세요. 합의되지 않은 각도·배속·PID 변경으로 넘어짐을 가리지 마세요.

8. **실제 C++ SDK와 ROS 연결 검증**

   현재 GUI 작업 폴더의 C++ `RobotMotionPlayer`는 프레임 최종각과 내부 시간 프로파일을 보내며, `gateCurrentFrame()`의 매 프레임 도착 대기와 최종 `updateSettling()`이 있습니다. 현재 로더는 `lift_early_arrival`, `playback_cycle_end`를 보존하지 않습니다. GUI와 이미 같다고 가정하지 말고 실제 알고리즘이 링크하는 버전의 코드를 확인해 필요한 부분을 구현해 주세요.

   ROS 실행기가 `startPoseTransition`, `updateStartupPose`, `setPositionToleranceEnabled`, `setJointOverride`, `clearJointOverride`, `DynamixelMotionHardwareConfig` 등을 요구한다면 실제 SDK의 지원 및 호출 효과를 확인하세요. 현재 작업 폴더의 실제 SDK에는 이 항목들이 없고 `queueNext`, `completionSequence`는 있습니다. `setJointCorrection`은 가산 보정이므로 값을 교체하는 override와 동일시하면 안 됩니다. mock에서만 지원하거나 호출을 무시하는 상태로 완료 처리하지 마세요.

9. **검증 방법과 완료 기준**

   먼저 모터 연결 없이 실제 GUI 계산 함수를 참조 실행기로 사용하고 실제 알고리즘 플레이어에 같은 초기각·JSON·가상 시각·통신 지연을 넣어 비교해 주세요. GUI를 임의로 재구현한 테스트끼리 비교하는 것만으로 완료하지 마세요. 실제 하드웨어 생성자는 열지 않고 통신만 mock으로 대체할 수 있게 분리하세요.
